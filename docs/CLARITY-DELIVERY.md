# Clarity & Delivery｜v0.7

v0.7 解决一个明确失败：为了降低模板感，系统把“宏观结构清楚”误伤成了“AI模板”，导致文章有判断却难读、标题承诺无法快速兑现。

核心原则：

> 宏观结构清晰，微观表达自由。

数字编号、清晰小标题、结论先行本身不是AI味。AI味来自机械重复的段落动作、均匀节奏、空泛过渡和标准化反转。

## 1. Reader Contract

每篇文章在进入 Architect 时必须冻结一个 Reader Contract：

- `promise_type`：标题向读者承诺什么
- `promise`：读者为什么点开
- `core_answer`：全文最重要的一句答案
- `answer_shape`：正文用什么形状交付答案
- `delivery_units`：读者读完明确拿走的2–6个单元

### promise_type

- `which`：哪些/哪几类/谁
- `how`：怎么做/如何
- `why`：为什么
- `compare`：A和B怎么选
- `decide`：值不值得/该不该
- `explain`：一个变化到底意味着什么
- `list`：明确清单/工具/步骤
- `other`

标题承诺决定正文交付形状。标题问“哪些”，正文必须明确回答“哪几类”；标题问“怎么做”，正文必须给步骤或动作；标题问“值不值得”，正文必须给判断标准和结论。

## 2. Thesis Prominence

Standard/Deep 的核心结论不得埋在后半篇。

默认要求：
- 前300个中文字符内出现 `core_answer` 的等价表达；
- 第一屏说明“这篇会给读者什么”；
- 若标题是问题型，第一屏先给方向性答案，再展开证据；
- benchmark、模型参数、政策背景等支持性证据默认放在结论之后。

例外：强叙事/调查稿可以延迟结论，但必须由 Architect 明确记录理由。

## 3. Macro Framework

对于知识型、工具型、决策型、政策解读型公众号文章，默认使用清晰编号框架：

`01 / 02 / 03 / 04`

尤其当标题包含：
- 哪些
- 几类
- 怎么
- 如何
- 哪几步
- 哪些工作
- 应该做什么
- 清单

则 `numbered_framework` 默认必选。

编号框架不是要求每节长度一致，而是给读者导航。每个小标题必须是“信息标题”，例如：

- 好：`01｜文献研究：先把“搜、下、整、比”交出去`
- 差：`01｜文献研究`
- 更差：`01｜发生了什么`

## 4. Delivery Units

每个主要章节必须交付一个具体单元，而不是只承担“解释功能”。

Delivery Unit 至少包含：
- `label`：读者拿走什么
- `answer`：一句清晰答案
- `concrete_examples`：至少一个具体任务/案例/动作
- `evidence_refs`：必要证据

如果一个章节只有抽象判断，没有具体对象、动作、数字、案例或决定，它通常还没写完。

## 5. Concrete Task Rule

对于“哪些工作/哪些场景/怎么做”类标题，正文必须下钻到任务级，而不是停在大类。

例如：

“文献研究”太大。

应该继续拆成：
`搜索 → 下载 → 去重 → 提取研究问题/数据/方法 → 建Literature Matrix → 标研究缺口`。

“数据分析”太大。

应该拆成：
`导入 → 清洗 → 改格式 → 跑代码 → 看报错 → 重跑 → 出图 → 导出`。

读者必须能想象这件事明天如何发生在自己的电脑上。

## 6. Evidence Salience

证据服务结论，不和结论争抢第一屏。

除非标题本身就是“某Benchmark意味着什么”，否则：
- 不要连续用多个Benchmark名开头；
- 不要在核心结论前堆模型参数；
- 每个技术指标出现时必须立即回答“它为什么改变本文结论”。

## 7. Framework ≠ Template

允许并鼓励：
- 01/02/03/04
- 前文先给结论
- 一个总框架 + 几个具体分类
- 小标题承担导航

仍然禁止：
- 每节长度接近
- 每节都“总结→解释→总结”
- 每节都有一次“不是…而是…”反转
- 每节末尾都升华
- 每篇固定“三条建议”

所以 Anti-Template 只打击微观重复，不再打击清晰宏观框架。

## 8. First-Screen Gate

前300字默认需要完成三件事中的至少两件，并且必须包含第一件：
1. 核心结论/方向性答案
2. 文章明确交付什么框架
3. 一个足够具体的事实/场景作为可信入口

禁止第一屏主要由：
- Benchmark缩写
- 模型参数
- 新闻背景复述
- 空泛时代判断
组成。

## 9. Promise → Delivery Gate

完稿后逐项核对标题承诺：

- `which`：是否给出明确分类，并逐类回答？
- `how`：是否给出可执行步骤？
- `why`：是否给出有层次的因果链？
- `compare`：是否存在同口径比较？
- `decide`：是否给出判断标准、代价和结论？
- `list`：是否真的提供了标题承诺数量/清单？

不能让读者从全文自己总结标题答案。

## 10. POV 选择的新标准

v0.6 只强调“更深”不够。v0.7 中三个POV竞争必须同时评价：

- `novelty`：是不是人人都会说
- `reader_value`：读者拿走什么
- `specificity`：能否落到具体任务/决定
- `frameworkability`：能否形成清晰交付结构
- `evidence_strength`：证据够不够

最深的POV不一定获胜；最适合公众号交付的POV才获胜。
